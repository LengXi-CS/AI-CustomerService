# 微信原生引用回复调研

调研日期：2026-10-13。

## 结论

GeWe 官方支持发送引用消息。2026-10-13 实测：简化模板在企业微信端呈现带分隔线的文字；使用真实手工引用的完整模板，仅替换回复正文后，用户截图确认企业微信端原生引用显示成功。完整模板回放路径已验证，仍需实现任意新消息的引用元数据采集、自动组装及延迟恢复 ID 修复，再接入生产回复流程。

## 官方依据

- [发送 appmsg 消息](https://doc.geweapi.com/api-139908321)：`POST /gewe/v2/api/message/postAppMsg` 支持引用消息；官方要求先从手工引用消息的回调保存结构，再替换 `svrid`（被引用消息的 `newmsgid`）及 `title`（回复正文）。
- [回调结构 v1.0](https://doc.geweapi.com/doc-3599831)：引用消息属于 `MsgType=49`，`appmsg.type=57`。

## 项目核查与本地验证

1. `adapters/wechat/client.py` 的 `send_quoted_text()` 使用上述端点，生成 `type=57` 和 `refermsg`；现有发送流程只调用 `send_text()`。
2. 通过 HTTP MockTransport 做了本地验证，确认生成的 XML 可解析，原消息 ID 写入 `refermsg/svrid`，回复正文写入 `title`，正文中的 `&`、`<` 正确转义。本地模拟不能证明微信客户端显示正常。
3. 用临时状态库及加密 payload 库验证 `process_conversation_task()`：持久化 payload 中的 `message_id` 是微信原始 ID，但恢复后的 `event.message_id` 是内部事件 UUID。这与官方要求的 `newmsgid` 不符，接入引用发送前必须修复。
4. 现有封装将被引用消息类型固定为文本，并用发送者 ID 充当显示名；先验证文本消息，图片、文件及引用消息需要按实际回调模板分别处理。

调研阶段未调用真实消息发送接口，未修改生产代码、配置或会话状态。

## 实施及验证顺序

1. 修复延迟恢复的微信消息 ID，继续以字符串保存，避免长整数精度损失。
2. 采集测试群中手工引用一条文本消息的真实回调模板，并核对发送者、群 ID、消息类型与显示名。
3. 在获授权的测试群发送一条原生引用回复；确认微信显示引用气泡、原文及回复内容正确，点击引用可定位原消息。接口返回成功只算接口受理。
4. 验证后接入合并后的安抚回复，并将引用关系写入聊天归档；原生引用不可用时，用带事项摘要的普通文字回复。

负责人私聊提醒的失败原因已由用户确认：机器人未添加负责人为好友。后续在好友关系建立后验证私聊送达。

## 2026-10-13 测试群接口发送结果

用户授权引用测试群内的“你好123”回复。已定位到 `AI客服测试（外部）` 中 08:48:51 的文本消息，并直接调用现有 `send_quoted_text()`，发送一条“你好，已收到。这是一条引用回复测试。”。

GeWe 返回 `ret=200`、`msg=操作成功`，并返回新的微信消息 ID；发送对象确认是测试群。已在聊天归档中记录引用关系，发送通道为 `quote_test`。未修改机器人回复逻辑或需求任务状态。

接口发送成功已确认；客户端显示结果见下节。点击引用能否定位原消息仍未确认。

## 2026-10-13 微信与企业微信客户端对比

用户提供同一条测试回复在两个客户端的截图：

- 微信端显示原生引用，引用摘要为“刘英豪: 你好123”。
- 企业微信端显示单个文字气泡，内容包含“[微信用户：你好123]”、分隔线及回复正文，没有微信端的原生引用样式。

现有发送方法只提交 `type=57` 的 XML，并未主动拼接上述文字分隔线。能确认现有模板在企业微信侧被以文字形式呈现，尚不能仅凭截图判断转换发生在 GeWe、微信与企业微信的互通链路，还是企业微信客户端。

查阅 GeWe 的 `postAppMsg` 文档，未找到其针对企业微信客户端原生显示的兼容保证。文档要求以实际手工引用回调为模板；当前方法是手写的简化结构，需要继续做对照。

用户随后完成手工对照：“这是回复”在微信及企业微信均显示原生引用，引用的原消息 ID 与 bot 测试一致。因此该群支持微信手工引用在企微原生显示，需继续排查 bot 的模板或接口发送路径。

在两端兼容性验证前，生产群可使用简短事项摘要的普通文本回复，配合需求去重，保证客户能识别回复对象。

## 字段顺序试验及完整回调采集

参考 [gewechaty 的引用实现](https://github.com/gewechaty/gewechaty/blob/main/src/action/common.js)，将群引用中的 `fromusr` 调整为群 ID、`chatusr` 调整为原发送者 ID。保持其余结构不变，向同一测试群发送“引用回复测试（二）：已调整群与发送者字段，请查看企微引用显示。”。接口再次返回成功，但用户截图显示企微仍为文字气泡，昵称从“微信用户”变为“刘英豪”。仅交换字段不足以解决原生显示，不能把该试验当作修复完成。

此前的聊天归档只保留引用摘要及引用图片 XML，手工引用文本消息的完整 XML 在解析后被丢弃，无法事后恢复“这是回复”的完整结构。

已为引用消息增加聊天归档字段 `metadata.raw_quote_xml` 与 `metadata.raw_quote_msg_source`，保留回调 Content 与 MsgSource 原文。沿用项目已有明文聊天库，仅归档已配置群，不将正文写入会话状态库。已通过相关 60 项测试与 Ruff 检查，采集代码需重启服务后生效。

重启后，再用普通微信账号手工引用“你好123”，回复“手工引用采集测试”。然后执行：

```powershell
.venv\Scripts\python.exe -X utf8 scripts/show_quote_template.py --text "手工引用采集测试" --output "data/quote-tests/manual-quote.xml"
```

该脚本只读聊天库，默认只显示节点名称；指定 output 时将完整原文导出到本地。下一轮以该真实模板对照实验，不继续仅凭第三方模板猜测字段。

## 完整手工模板回放试验

重启后已成功采集“这是第二次回复”（09:08:18）的完整回调，原文导出到 `data/quote-tests/manual-quote.xml`。其引用对象仍为“你好123”。

真实 `refermsg` 包含 `content`、`createtime`、`displayname`、`fromusr`、`svrid`、`msgsource`、`strid`、`type`、`chatusr`、`fromusername_to_imunion`。简化发送模板缺少原消息时间、消息来源、字符串消息标识及企业微信身份关联字段。`fromusr` 为群 ID，`chatusr` 为原发送者 ID，与上轮调整一致，但上轮实测已证明只交换这两个字段不够。

已授权测试继续使用同一测试群和同一条“你好123”：从真实回调截取完整 `appmsg`，保留所有结构及引用元数据，仅替换 `title` 为“引用回复测试（三）：这次使用完整手工引用模板，请查看企微是否显示原生引用。”。发送前核验消息类型、原消息 ID、群 ID及引用原文，模板保存到 `data/quote-tests/replay-quote.xml`。

接口返回 `ret=200`、`msg=操作成功`，已记录聊天归档。用户随后提供截图，确认企微客户端原生引用显示成功，原发送者及“你好123”引用正文正常。该试验验证了完整模板回放，不足以确定单一缺失字段的必要性，也尚未实现任意新消息的自动引用。点击引用定位原消息的行为仍未单独确认。
