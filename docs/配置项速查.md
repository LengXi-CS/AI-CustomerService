## 〇、先搞清楚：每个参数的值从哪来

配置分三层，但**更关键的是每一项的「值」本身怎么拿到**。下面按来源分类。

### 0.1 三层配置文件

| 层级 | 文件位置 | 管理方式 | 是否入库 |
|---|---|---|---|
| 密钥与端点 | `.env`（项目根） | 手工编辑 | 否（已 gitignore） |
| 群策略 | `config/wechat_groups.toml` | 手工编辑 | 是（不含密钥） |
| 代码默认值 | `src/fastgpt_assistant/core/config.py` | 环境变量覆盖 | 是 |

### 0.2 每类参数的具体获取途径

| 参数类别 | 从哪获取 | 具体操作 |
|---|---|---|
| **群 ID** `group_id` | **从回调日志里抄** | 客户在目标群发一句话 → 打开 `logs/5330.err.log` → 搜 `chat=xxx@chatroom` → 复制该串 |
| **客服/负责人 wxid** | **从回调日志里抄** | 让该客服在群里发一句话 → 日志 `sender=wxid_xxx` → 复制（群聊中通常是 `@openim` 结尾的长串） |
| **机器人 wxid** `BOT_WXID` | 回调日志 / `.env` 已有 | 日志里 `to_user` 或消息发送方；当前已配置 |
| **机器人昵称** `bot_aliases` | **需人工确认** | 问负责人机器人微信昵称，或看它在群里被 @ 时的显示名 |
| **GeWe Token / AppID** | GeWe 后台 | 登录 api.geweapi.com 控制台 → 实例详情页 |
| **FastGPT API Key** | FastGPT 控制台 | 登录 → 账号 → API 密钥 |
| **FastGPT Dataset ID** | FastGPT 知识库 | 打开知识库 → 地址栏 `/dataset/detail?id=xxx` |
| **DeepSeek API Key** | DeepSeek 开放平台 | platform.deepseek.com → API Keys |
| **飞书应用凭证** | 飞书开放平台 | open.feishu.cn → 开发者后台 → 凭证与基础信息 |
| **飞书多维表格 Token** | 表格 URL | 打开表格 → 地址栏 `base/xxx?table=tblxxx` |
| **公网回调地址** | 由 frp/cpolar 决定 | 跑 `python scripts/get_public_url.py` 查询当前地址 |
| **端口 5330** | 启动脚本决定 | `scripts/start_server.ps1` 内硬编码 |
| **各超时/阈值** | 源码默认值 | `core/config.py`，一般无需改 |

### 0.3 获取群 ID 与 wxid 的完整流程（最常用）

这是接入新群时**必做**的第一步。源码层面，`group_id` 来自 GeWe 回调的 `FromUserName.string` 字段（见 `engine.py:487` / `engine.py:543`），群聊的特征是**以 `@chatroom` 结尾**。

```bash
# 第 1 步：让客户在目标群里发任意一条消息
# 第 2 步：实时跟踪日志，抓取 chat 与 sender
tail -f logs/5330.err.log | grep "Received WeChat event"
```

日志会打印成这样（真实样例）：

```
Received WeChat event chat=49195424680@chatroom sender=25984983404774216@openim role=customer mentioned_bot=False type=1
```

- `chat=49195424680@chatroom` → 这就是 **`group_id`**
- `sender=25984983404774216@openim` → 这是**发送者 wxid**，填进 `customer_service_ids` 即为客服身份
- `role=customer` → 角色判定结果，若该人应是客服却显示 `customer`，说明 wxid 没填对

> 群 ID 形如 `一串数字@chatroom`，不是 `wxid_` 开头。两者不可混淆。

### 0.4 获取公网回调地址

```bash
python scripts/get_public_url.py
```

拿到地址后写回 `.env`：

```bash
python scripts/set_public_base_url.py https://xxxx.r11.cpolar.top
```

## 一、群策略配置项

**文件**：`config/wechat_groups.toml`
**加载器**：`core/wechat_groups.py`（`WechatGroupsProvider`）
**生效方式**：**热加载** —— 改动后下一跳消息即生效，**无需重启服务**
**容错**：文件缺失时 **fail closed**（所有群按未授权处理）；TOML 写坏时**保留上一份可用配置**并落日志，服务不中断

### 全局段 `[global]`

| 参数 | 类型 | 默认 | 值从哪来 | 说明 |
|---|---|---|---|---|
| `enabled` | bool | `false` | 自行决定 | 总开关 |
| `reply_to_staff_when_mentioned` | bool | `true` | 自行决定 | 客服 @机器人 时是否回复 |
| `soothe_mode` | enum | `model` | 自行决定 | 安抚话术来源：`model` 模型现写 / `fixed` 固定文案，详见下节 |
| `soothe_fixed_reply` | str | `"收到，我们加急处理"` | 自行决定 | `soothe_mode = "fixed"` 时使用的那句话 |

### 群段 `[[groups]]`

| 参数 | 类型 | 默认 | 值从哪来 | 说明 |
|---|---|---|---|---|
| `group_id` | str | **必填** | **回调日志 `chat=`** | 群 ID，以 `@chatroom` 结尾，不可重复 |
| `group_name` | str | `""` | 问负责人 | 仅备注，不参与逻辑 |
| `mode` | enum | `disabled` | 自行决定 | `disabled` 忽略 / `shadow` 只记录不发 / `active` 正常回复 |
| `require_customer_mention` | bool | `false` | 按群运营策略 | 客户是否必须 @机器人 |
| `allow_images` | bool | `true` | 自行决定 | 是否接收图片 |
| `allow_files` | bool | `true` | 自行决定 | 是否接收文件 |
| `owner_id` | str | `""` | **回调日志 `sender=`** | 负责人 ID，非标准需求时私聊通知。个人微信是 `wxid_...`；企业微信成员在外部群里是 `数字@openim`，**角色匹配同样有效，但 GeWe 能否向其发私聊需实测**（发一条非标准需求后看 `logs/5330.err.log` 是 `Owner reminder delivered privately` 还是 `failed`） |
| `customer_service_ids` | list | `()` | **回调日志 `sender=`** | 客服 wxid 名单，决定角色判定 |
| `bot_aliases` | list | `()` | **问负责人要昵称** | @识别兜底，当前为空 |
| `reply_to_staff_when_mentioned` | bool | `true` | 自行决定 | 群级覆盖全局 |

### 安抚话术模式（2026-09-23 新增）

「安抚」指**非标准需求**（未命中任何标准意图）时回给客户的那一句——按 2026-09-18 决策，
这条路径只安抚、绝不反问，同时私聊提醒群负责人。这句话有两种来源：

| `soothe_mode` | 客户收到什么 | 模型调用 | 适用场景 |
|---|---|---|---|
| `model`（**默认**） | 模型现写一句，措辞每次不同 | 每次 1 次 | 希望读起来像真人、不像模板 |
| `fixed` | 固定一句 `soothe_fixed_reply` | **0 次** | 希望措辞完全可控、可审计、省调用 |

```toml
[global]
soothe_mode = "model"                    # 改成 "fixed" 即启用固定文案
soothe_fixed_reply = "收到，我们加急处理"  # fixed 模式实际发出的那句
```

**三个必须知道的点**：

1. **改完即生效，无需重启**。这两个参数走的是群策略文件的热加载通道（改 `config/wechat_groups.toml`，下一跳消息生效）。
2. **默认仍是 `model`**，与改动前行为完全一致——升级不会悄悄换掉线上话术。
3. **固定文案只影响「安抚」这一条路径**，不碰「资料不足」（`INSUFFICIENT_DATA_FALLBACK_REPLY` 那条）也不碰澄清问句。
4. **兜底仍在**：`model` 模式下模型不可用时回 `query_routing.NON_STANDARD_SOOTHE_REPLY`；`fixed` 模式下若 `soothe_fixed_reply` 被写成空串，也会退回模型生成，不会发出空消息。

### 关键机制

1. **白名单制**：未在 `[[groups]]` 列出的群，默认拒绝处理。
2. **角色判定**：`sender_role()` 查 `customer_service_ids`，命中即 `staff`，否则 `customer`。`owner_id` 若不在名单会被**自动前置插入**，保证负责人一定被识别为客服。
3. **`bot_aliases` 为空的风险**：当前为 `[]`。若 GeWe 不回传显式 @ 字段，@机器人 可能识别失败。**建议确认昵称后立即补全。**
4. **热加载**：本文件按 `(mtime_ns, size)` 戳监听，改完**下一跳消息即生效，无需重启**。写坏 TOML 时会保留上一份可用配置并落 `logger.exception`，不会打断正在服务的群；把文件删掉则 fail closed（全局停用群处理）。

## 二、回复节奏

**核心机制**：**静默窗口 + 轮询认领**，不是收到消息立即回复。

### 参数表

| 参数 | 默认 | 环境变量 | 值从哪来 | 说明 |
|---|---|---|---|---|
| 静默窗口 | **120 秒** | `CONVERSATION_QUIET_WINDOW_SECONDS` | 代码默认 | 客户最后一条消息后等待时长 |
| 轮询间隔 | **30 秒** | `CONVERSATION_POLL_INTERVAL_SECONDS` | 代码默认 | 调度器扫描周期 |
| 单批上限 | **20 条** | 硬编码 `batch_size` | 代码 | 每轮最多认领任务数 |
| 附件发送间隔 | **5.0 秒** | `ATTACHMENT_DISPATCH_INTERVAL_SECONDS` | 代码默认 | 连发多个文件/图片时的停顿 |

> ⚠️ **以上三项当前 `.env` 中均未配置，跑的是代码默认值。**

### 完整时序

```
客户发言
  └→ 写入 conversation_events，任务状态 = waiting_quiet
       └→ 等待 120s 静默窗口（期间客户再发言 → 计时重置）
            └→ 轮询器每 30s 扫描，认领到期任务（状态 → processing）
                 └→ 执行查询 → 发送回复 → 状态 = responded
```

### 实际感知延迟

- **最快约 120 秒**（静默到期恰好赶上轮询落点）
- **最慢约 150 秒**（120s 静默 + 最多 30s 轮询延迟）
- 客户连续发言时，**从最后一条算起**重新计 120 秒

### 人工介入拦截（防抢单，核心保障）

`claim_ready_tasks()` 的 SQL 硬条件：

```sql
WHERE state = 'waiting_quiet'
  AND latest_customer_at <= :cutoff          -- 静默窗口已过
  AND (last_staff_at IS NULL OR last_staff_at < latest_customer_at)
```

**只要客服在客户之后发言，该任务永远不会被自动回复**，直接让位人工。

### 异常重试

任务抛异常时状态回滚为 `waiting_quiet`，重走一轮静默窗口后重试（无最大重试次数限制）。

### 状态流转

```
waiting_quiet → processing → responded   正常
waiting_quiet → blocked                  payload 缺失 / 保险库不可用
waiting_quiet → closed                   需求文本为空
任何状态      → blocked                  解析失败
```

## 三、路由策略与机制

**文件**：`orchestration/query_routing.py` → `decide_query_route()`

### 参数表

| 参数 | 默认 | 环境变量 | 说明 |
|---|---|---|---|
| 正常阈值 | **0.80** | `ROUTING_NORMAL_CONFIDENCE_THRESHOLD` | `intent_confidence` 达到才自动回复 |
| 人工阈值 | **0.50** | `ROUTING_HUMAN_CONFIDENCE_THRESHOLD` | 低于此值直接静默 |
| 负责人通知 | **true** | `OWNER_NOTIFY_ENABLED` | 是否私聊提醒负责人 |

**约束**：必须满足 `0 <= human_threshold <= normal_threshold <= 1`，否则启动即抛 `ValueError`。

> 这两个阈值由**模型输出的置信度**驱动，不需手工采集，调参靠观察实际效果。

### 五种输出行为

| kind | 触发条件 | 客户看到什么 |
|---|---|---|
| `normal` | 意图与实体都达标 | 正常回答 |
| `clarify` | 标准需求但缺实体 | 反问澄清（如「请问您想查询哪个品牌？」） |
| `human` | 明确要人工，或中等意图 | 「请 @ 负责人」/「我暂时无法准确确认」 |
| `silent` | `intent < 0.50` | **什么都不回** |
| `soothe` | 非标准需求 | 安抚话术 + 私聊提醒负责人 |

### 判定优先级（固定顺序，不可随意调整）

```
1. 显式人工请求        → human    关键词：转人工/找客服/找负责人 等 10 个短语
2. intent < 0.50       → silent   最高优先，防误答
3. 非标准需求          → soothe   仅当 channel != "structured"
4. structured 且
   completeness < 0.80 → clarify  澄清闸门（第一道）
5. channel ==
   "clarify"           → clarify  澄清闸门（第二道）
6. intent < 0.80       → human    中等意图转人工
7. 其余                → normal
```

### 两个必须理解的机制

**1. 三重独立闸门，不是一个融合分数**

- `intent_confidence` → 能不能回答
- `completeness` → 能不能执行
- `demand_kind` → 允不允许反问

> 源码注释记载：早期版本把三个信号融合成一个数，导致「一张模糊图片拖垮整个评分」，把本来理解清楚的需求给静默掉了（架构诊断文档「根因 3」）。

**2. 澄清闸门刻意排在转人工之前**

2026-09-18 负责人决策。实测证据：

| 输入 | intent | completeness | 旧行为 | 现行为 |
|---|---|---|---|---|
| `这两款检测报告麻烦提供下` | 0.72 | 0.25 | 转人工 | **澄清** |
| `查一下产品` | 0.55 | 0.20 | 转人工 | **澄清** |

两者都是「标准需求、只缺实体」，旧逻辑下客户永远拿不到那句本该问的澄清。

**3. 非标准需求只安抚，绝不反问**

「只安抚」对非标准需求是**无条件规则**——反问「请问您想查询什么」正是要消除的群内噪音。负责人提醒本身已完成交接。安抚话术**不写死**，由 `compose_soothe_reply` 逐条生成，失败才回退固定模板。

## 五、群聊天记录库（本地归档，2026-09-23 新增）

**文件**：`data/chat-log.db`（SQLite，`data/` 已 gitignore，**不会推到 GitHub**）
**代码**：`core/chat_log.py`（`ChatLogStore`）
**写入时机**：回调进来时**先归档再路由**，以及机器人**实际发出**回复之后
**存储形式**：**明文**（明文便于直接查询、后续可整体迁移到正式库；代价是本机文件可读）

### 存了什么

只存 **`config/wechat_groups.toml` 里已配置的群**，私聊与未配置群一条都不写。

| 列 | 含义 |
|---|---|
| `id` | 自增主键，前端增量拉取的游标 |
| `chat_id` / `chat_name` | 群 ID / 群名（取自群配置的 `group_name`） |
| `message_id` | 平台消息 ID（出站为空） |
| `direction` | `inbound`（客户/客服）/ `outbound`（机器人） |
| `sender_id` / `sender_name` / `sender_role` | 发送者 wxid / 显示名（GeWe 不给则空）/ `customer`·`staff`·`assistant` |
| `kind` / `msg_type` | 渲染类型（`text`·`image`·`file`·`voice`·`video`·`other`）/ 原始 GeWe `MsgType` |
| `text` | 消息正文（图片为空，类型由 `kind` 表达） |
| `quoted_msg_id` / `quoted_type` / `quoted_text` | 引用消息的消息 ID / 类型 / 摘要 |
| `media_ref` / `media_name` / `media_mime` / `media_size` | 附件引用（入站图片为 `inm_<消息ID>`）、文件名、MIME、字节数 |
| `channel_used` / `task_id` | 出站回复走的渠道（`soothe`/`clarify`/`structured`…）与关联任务 ID |
| `metadata` | JSON 扩展位：`mentioned_bot`、`mentions`（被 @ 的昵称，解析器会从正文里删掉，这里留着复现）、`quoted_media_xml` |
| `occurred_at` / `recorded_at` | 事件时间 / 入库时间（均为 UTC ISO） |

**幂等**：入站按 `(direction, chat_id, message_id)` 去重——GeWe 重试回调不会长出重复气泡；出站无平台 ID，每次都新增（每次真实发送都是一条记录）。

**不记什么**：影子模式（`mode = "shadow"`）的回复**没真发出去**，不记；机器人私聊负责人的提醒属于**另一个会话**，不在群记录里；**发送失败的出站也不记**——`dispatch_outbound` 返回 `DispatchOutcome`，只有文本/附件真正发成功的部分才落行，档案里不会出现「显示已发出、实际没发到」的假气泡。

### 开关与配置（`.env`，改动需重启）

| 变量 | 默认 | 说明 |
|---|---|---|
| `CHAT_LOG_ENABLED` | `true` | 总开关，`false` 则只建表不写入 |
| `CHAT_LOG_DB_PATH` | `data/chat-log.db` | 库路径 |

### 怎么查看

```bash
# 有哪些群、各多少条
.venv\Scripts\python.exe scripts/show_chat_log.py

# 某群最近 30 条（正序，含引用/@/附件/渠道）
.venv\Scripts\python.exe scripts/show_chat_log.py --chat 49195424680@chatroom

# 增量拉新（前端用同一套 id 游标）
.venv\Scripts\python.exe scripts/show_chat_log.py --chat 49195424680@chatroom --after 128

# JSON 行，直接喂前端调试
.venv\Scripts\python.exe scripts/show_chat_log.py --chat 49195424680@chatroom --json
```

`GET /health` 的 `chat_log` 字段可确认开关状态与库是否已生成。

> ⚠️ **目前没有清理策略**，表会一直增长。长期运行前需要定一个按时间或条数的保留策略。

```python
# 以 llm_model 为例，四种写法指向同一参数
LLM_MODEL / MODEL_NAME / DEEPSEEK_MODEL / EA_DEEPSEEK_CHAT_MODEL
```

> ⚠️ 现存问题：`.env` 内混用了 `EA_` 前缀与无前缀写法。当前都能生效，但建议统一为无前缀形式。
