# 按原始需求生成安抚话术

实现日期：2026-10-15。

2026-10-16更新名片过滤及历史任务恢复规则。最新代码基线和服务加载核验见[项目现状与验收](项目现状与验收.md)；下文分日期验证为当时记录。

`soothe_mode = "model"` 时，将本次需求的客户原话交给已配置的模型，生成一句针对该事项的简短安抚。提示词在 `src/fastgpt_assistant/adapters/llm/chat_model.py` 的 `SOOTHE_COMPOSER_SYSTEM_PROMPT`。

## 链路

1. 先按消息类型和群策略筛选，再建立需求任务；按对应群的有效等待时间调度。人工已接管、需求已关闭或已安抚时，继续沿用原来的发送限制。按群等待配置见[WebUI说明](群管理WebUI.md)。
2. 延迟恢复时，从加密 payload 恢复各条需求原文。已关联为同一事项的消息按原有顺序保留，第一条作为原始需求，其余作为补充。尚未关联的需求继续分别处理。
3. 判断需要安抚后，先检查负责人提醒配置，再把原始需求、补充、引用上下文、群上下文、历史及绑定图片交给模型。上下文只辅助理解，不能替代当前需求。
4. 模型输出15～35字为主、最多50字的一句纯文本，点出客户关心的事项，不解答尚未核实的业务问题。
5. 清理格式与换行，检查长度、追问、常见的已完成动作或时效承诺。模型异常、空回复或检查未通过时，使用“收到，您反馈的情况我看到了。”。
6. 通过现有发送组件发送；引用气泡仍取决于逐群引用配置和原消息类型。负责人提醒沿用现有私聊发送流程。

## 模型输入

沿用全模态任务协议，在 user 消息中增加 `reply_context`：

```json
{
  "task_id": "当前需求任务ID",
  "demand": "本次完整需求，包含已关联的补充",
  "quote": {
    "message_id": "客户引用的消息ID",
    "type": "原消息类型",
    "text": "引用原文",
    "related_context": "引用相关上下文"
  },
  "group_context": "已选取的群上下文",
  "reply_context": {
    "original_request": "客户最初的需求原话",
    "related_customer_messages": ["同一需求的后续补充原话"],
    "allowed_actions": ["反馈核实"]
  }
}
```

文本原话不先交给另一个模型概括，也不为了安抚而截断。文件传输 XML 继续转为附件说明，避免把传输密钥交给模型。图片使用同一任务已绑定的图片块。

只有同时开启负责人通知、配置了当前群及负责人、且生成了待发送提醒时，`allowed_actions` 才包含“反馈核实”。它表示可将需求反馈给负责人，不代表已经送达、已经核实或能持续查询进度。没有通知渠道时传空数组，只确认收到并理解需求。

独立需求拆分后各自传入自己的原文，不把其他需求放入其 `original_request` 或补充数组。群上下文中的其他客户消息仍只作为带身份的参考材料。

## 话术目标

- 点出客户关心的规格、价格、漏发、到货等事项，不抄整段需求或订单号。
- 不确定时使用“这个情况”等表达，不编造需求对象。
- 不追问、不要求补资料，不把客户陈述的价格、规格或约定当成已核实事实。
- 不声称“已经核实／已经发货／已通知”，不承诺加急、处理时限、处理结果或稍后答复。
- 自然、简短，不固定要求每次都提“负责人”。

## 验证与生效

相关回归覆盖模型实际请求体中的原文和补充、引用及图片传递、延迟恢复、独立需求隔离、通知关闭或负责人缺失、异常输出回退，以及固定话术模式兼容。真实模型试调用仅生成预览，不向微信发送，也不修改在线任务。

2026-10-15 验证：全量 `pytest -q` 为532项通过，`ruff check src tests` 与 `git diff --check` 通过。最终提示词的真实模型预览包括：

- “这单签收单上少了一款商品”＋“请核实是不是漏发了” → “收到，签收单缺项的漏发疑问我这边反馈核实一下。”
- “这个酒精还是发60ml的、金额1.65对吗？” → “酒精的规格和金额，我这边反馈核实一下。”

模型措辞会随输入及采样变化；预览验证了当前提示词能围绕具体事项回应，并保留待核实状态。

提示词与输入链路属于 Python 代码变更，服务重启后生效。`soothe_mode` 仍通过 `config/wechat_groups.toml` 热加载；切到 `fixed` 时仍直接使用配置的固定话术。

## 名片分享误触发安抚的补修（2026-10-16）

“AI客服测试（外部）”群14:55–14:57的7条企业微信名片回调均为MsgType 66。原回调入口把非空Content当成文字需求，名片XML因此进入拆分和任务创建。归并、恢复时，通用XML处理将其改写成“附件消息”，随后模型把合并后的多条附件判断为需要核实的非标准需求，14:57:53发送了安抚。前两条曾分别被判为不确定而静默，后续5条合并后误触发；调整提示词不能替代入口的消息类型判断。

现在个人名片42和企业微信名片66不创建需求、不调用拆分与回复模型、不重置等待，也不登记人工接管；客服发送及带@同样过滤。配置群中的名片继续归档并保留类型化上下文；私聊名片直接忽略，当前聊天归档只覆盖配置群。历史归档中的名片在当天上下文中也显示为名片，不再显示为附件；名片字段不进入需求模型。

重启后，旧版本已排队的名片任务在归并或恢复时会关闭；已回复名片的回执保留，但纯名片事项不再作为新文字需求的关联候选，避免把真实需求错误去重。混合事项仅移除名片成员，保留真实需求和对应引用来源。明确引用名片提出文字问题仍按正常需求处理，名片引用上下文以类型说明呈现。

回归覆盖连续分享、客服及@、私聊、等待窗口不被名片重置、无人工接管副作用、名片后的真实需求、引用名片的文字问题、旧排队任务、混合事项、历史归档及重启恢复。真实7条名片在临时数据库和模拟微信传输中回放：归档7条，创建需求0条，模型调用0次，自动发送0次。回放脚本与结果为`outputs/replay_contact_cards.py`及`outputs/contact-card-replay.json`；原生产归档只读，没有重发真实消息。本轮新代码仍需重启后生效。

最终验证：新增17项回归，全量686项通过（285.93秒），`ruff check src tests`与`git diff --check`通过。候选事项仍只取最近4条有效需求用于模型输入，名片不占需求位置；没有因过滤名片而扩大正常事项的读取范围。最终测试日志和JUnit结果分别为`outputs/contact-card-tests-final.txt`及`outputs/contact-card-tests-final.xml`。
