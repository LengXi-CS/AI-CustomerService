## 4. 本次会话攻坚与关键修复

### 4.1 微信聊天气泡 100% 纯文本（Plain Text）改造
- **背景**：微信客户端无法渲染 Markdown 语法，原大模型输出包含 `**粗体**`、`### 标题`、`- 列表` 等符号，视觉杂乱。
- **解决方案**：
  1. 重写 `WECHAT_COMPOSER_SYSTEM_PROMPT`，禁止模型输出任何 Markdown 语法，改用 `【模块标题】`、`· ` 中文圆点等适合微信排版的纯文本格式；
  2. 实现 `clean_wechat_text` 文本清洗器，在向微信和 API 发送前进行正则保底过滤（自动剔除 `**`、转义 `#`、规范列表和空行）。

### 4.2 关联查询目标实体名称（如 factory_name）丢失修复
- **背景**：用户查询 `6976070461130 的商品信息和工厂` 时，Bot 仅输出了 `关联工厂ID：020001`，工厂名丢失。
- **原因**：规划器在 `select` 中带有了主表的外键 `factory_id`，导致 `_related_select` 过滤目标表字段时只保留了 `factory_id`，遗漏了 `factory_name`。
- **解决方案**：
  1. 优化 `query_engine.py` 的 `_related_select`：当目标实体字段仅匹配到 ID 外键时，自动补充默认展示字段（包含 `target_scope.name_column`，如 `factory_name`、`category_name` 等）；
  2. 优化 `adapters/llm/chat_model.py` 中的 `QUERY_PLANNER_SYSTEM_PROMPT`，引导模型在跨表查询时携带关联实体的名称字段。

### 4.3 客观事实性原则与杜绝虚假承诺
- **治理**：杜绝大模型在数据未记录时脑补客服承诺（如“安排人员跟进对接”等）。严格对齐原 LangBot 契约：只陈述事实，未记录字段直接如实简述“暂未记录”，不发散、不客套。

### 4.4 字段中文映射与类型容错
- **字段标签映射**：引入 `FIELD_LABELS` 和 `SCOPE_LABELS` 字典，将数据库英文字段名转换为业务中文标签；
- **Confidence 容错（2026-09-18 换代）**：原 `QueryPlan.confidence` 单数字段已拆为 `intent_confidence` + `completeness`（详见第 5 节规则 8 与第 10 节）。原 `_normalize_confidence` 的档位映射（`high`→0.9 / `medium`→0.6 / `low`→0.3）抽为 `_confidence_scalar()`，对**两个字段都生效**，行为未变。

## 5. 必须遵守的工程规则与避坑指南 (只增不删)

1. **绝对禁止泄露敏感凭证**：
   - 严禁提交、回显或在任何代码及测试文件中输出 `.env`、API Key、GeWe Token、微信个人隐私数据。
2. **多表关联查询字段选择（Related Select）**：
   - 跨表关联查询时，目标实体的描述性字段（尤其是名称字段 `*_name`）必须得到保障，不能只提取外键 ID。
3. **微信客户端格式契约**：
   - 微信消息绝不能包含 Markdown 代码块、加粗 `**`、斜体 `*` 或标题 `#`。必须使用清晰纯文本排版。
4. **服务代码热重载与进程管理**：
   - 修改Python源码后，当前Uvicorn进程不会自动热加载。本机由NSSM托管，应在管理员PowerShell执行 `scripts/restart_app.ps1`，而非手动强杀服务子进程；脚本先只读列出未终态任务、重启服务并检查健康。不要同时启动另一份5330进程。
   - **PID 属易失效信息，每次都要重新取证**（本文档记录的 PID 只是当时快照，例如 67912 早已失效）。取法：`netstat -ano` 查监听 5330 的 PID。
   - **终止前先确认 `ESTABLISHED` 连接数为 0**。若此刻 GeWe 正在拉取附件，强杀会掐断一次真实投递。cpolar 面板上出现不带状态码的 `GET /v1/media/...` 时尤其要警惕。
   - 重启日志建议用**追加**方式写 `logs/5330.out.log` / `logs/5330.err.log`，保留修复前旧行以便前后对照。
5. **穿透隧道保活（含历史cpolar经验）**：
   - 当前Docker/frpc回调隧道应保持运行；不要因AidNet也有frpc便混用进程。历史cpolar部署同样不可随意终止隧道，本文旧任务号仅为当时快照。
   - **回调探针必须带正确的 `X-Forwarded-Host` / `X-Forwarded-Proto`**。`observe_public_origin()` 会用该头覆盖运行中的媒体基址，若用 `127.0.0.1` 打探针，会把**正在服务的**外发基址污染成 localhost，导致后续附件 URL 失效。
   - 需要公网地址时向负责人索取（可从 cpolar 面板 Forwarding 行读取），**不要写入文档**。
6. **大体积文件、附件去重与微信穿透带宽**：
   - 免费 cpolar 上行带宽实测约 **90~95 KB/s**；GeWe 云端拉取 `fileUrl` 有内置下载超时（实测可容忍 ≥11.6 秒 / 1.09 MB 并成功）。
   - **附件必须按 `media_id` 去重后再下发**，且**严格串行**、每份之间留间隔。并发下发多份会争抢带宽并诱发 `文件下载失败:timeout`（已实机验证：同一份 1.17 MB 文件并发时失败、串行时成功）。
   - 已实现：`dedupe_deliverables()` + `dispatch_outbound` 串行 + `attachment_dispatch_interval_seconds`（默认 5 s）。**不要绕过或删除这三处逻辑。**
   - `/v1/media/{media_id}` 在返回文件前会记录真实字节数：`Serving media media_id=... size=<bytes> name=...`。这是判断"超时到底是不是体积导致"的第一手依据，**不要删除该日志行**（该行为 `logger.info`，依赖第 7 条日志配置才可见）。
7. **应用日志必须真正落盘（2026-09-18 已修复）**：
   - 历史缺陷：`server/app.py` 只设置 logger level、未配置根 logger handler，本项目 `logger.info` 全部被 Python `lastResort`（仅 WARNING+）丢弃。
   - 现状：`server/app.py` 提供 `configure_logging()` / `resolve_log_level()`，由 `lifespan()` 启动时调用一次。它会（且仅在根 logger 无 handler 时）调用 `logging.basicConfig`，并把 `fastgpt_assistant` 包 logger 设为 `settings.log_level`（`LOG_LEVEL` / `EA_LOG_LEVEL`，默认 `INFO`）。
   - 该函数幂等，不会重复挂 handler；**不触碰 `uvicorn.*`**（其自带 handler 且 `propagate=False`），uvicorn 日志格式与条数不变。
   - 排查时用 `LOG_LEVEL=DEBUG` 可临时放大到调试级；`uvicorn` 访问日志落在 `logs/5330.out.log`，**应用自身的 INFO 日志落在 `logs/5330.err.log`**（部署时 stderr 重定向到该文件）。
   - 新增诊断日志后，务必确认它真的出现在 `logs/5330.err.log` 中，不要假定"写了就一定看得到"。
8. **置信度合约：两个独立信号，禁止合成一个数（2026-09-18 起，只增不删）**：
   - `QueryPlan` 只有 `intent_confidence`（意图把握）与 `completeness`（实体/信息齐全度）两个信号。**不要再新增"综合置信度"字段，也不要把两者相乘或加权后拿来驱动路由。**
   - **静默由 `intent_confidence` 独占**（`< 0.50`）；`completeness` 偏低**只允许**导致"向客户反问"，绝不允许把已经听懂的需求静默掉。这一条是"图片一含糊就整体塌陷、需求漏识别"的正解，改动前先读 `架构诊断-越改越不如意的根因.md` 根因 3。
   - **纯告知/信息同步类消息必须静默**（2026-09-23 实测踩坑后补进规划器提示词规则 4/7）：运单号/订单号、金额与审核状态（"订单金额23470，已审核"）、付款回执说明、发货安排播报（"XX商品1箱分开发出"）等**陈述式**内容，只要没有请求语气（"帮我/请/能不能/查一下"），就不是需求——`demand_kind=non_standard` 且 `intent_confidence < 0.50`。客户曾在群里贴两条运单号，被误判为非标准需求，触发两条安抚 + 两条私聊负责人。注意边界：带请求语气的同内容（"帮我查一下这个单号"）仍是真实需求，不得静默。有专门测试守提示词（`test_planner_prompt_treats_informational_sync_as_silent`）。
   - `completeness` 闸门**只对 `channel == "structured"` 生效**；`narrative` / `direct` 没有实体可缺，不受它约束。
   - `QueryPlan.confidence` 是 `@computed_field`（取两者最小值），**仅供日志与 JSON 兼容，任何路由判断都不得读它**；它也**不接受赋值**——`model_copy(update={"confidence": ...})` 会被静默忽略（已踩过，别再用）。
   - **规划器上下文必须经 `planner_safe_analysis()` 脱敏**：`image_confidence` 与候选 `confidence` 只许留给 `resolve_visual_skus()` 做确定性晋升（`< 0.80` 剔除），**不得进入规划器提示词**；否则图片的识别不确定会被规划器当成"意图"的不确定。
   - 图片歧义分支的 `clarification` **必须构造 `QueryClarification`**；读取一律走 `clarify_question()`。原因：`model_copy(update=...)` **不做校验**，可能拿到普通 `dict`（该缺陷曾长期潜伏，见第 10 节）。
   - 兼容层 `_expand_planner_confidence()` 接受旧单数 `confidence`（复制到两个信号）以及"只给其一"的输出；**两个都不给才报 `ValidationError`**（不静默兜底）。**不要删兼容层**——FastGPT 侧工作流可能仍在发旧格式。
9. **需求类型合约：标准需求才澄清，非标准需求只安抚 + 私聊负责人（2026-09-18 起，只增不删）**：
   - `QueryPlan.demand_kind`（`"standard"` / `"non_standard"`）由规划器显式给出，**必须显式区分，不得靠推断**。默认 `"standard"` 是**有意的安全退化**（缺失即退回"向客户澄清"的旧行为），不要改成 `non_standard`。
   - **会议口径**：澄清属于标准需求——"命中标准需求但信息不足才澄清"；非标准需求**只安抚 + 提醒负责人**。这是为了消灭"误澄清/乱澄清"。
   - **路由顺序有硬约束**：`non_standard` 的安抚分支必须排在"中置信度转人工"闸门**之前**。否则 `intent_confidence` 落在 0.50~0.80 的非标准需求会退化成"请 @ 人工客服协助确认"（实测 `帮我改一下发票抬头` 的 intent 恰为 **0.620**，即不提前就必然复现该退化）。唯一例外：`channel == "structured"` 的计划属自相矛盾，仍走标准链路。
   - **安抚文案必须模型生成，不许写死**：走 `ChatModelClient.compose_soothe_reply()`（temperature 0.7）。`NON_STANDARD_SOOTHE_REPLY` **只是模型不可用时的兜底常量**，不是正常文案。**不得**复用 `WECHAT_COMPOSER_SYSTEM_PROMPT`——它明文禁止承诺"安排人员跟进"，而这条链路必须（且真实）承诺会转达负责人。
   - **提醒负责人是私聊，不是群内 @**（负责人 2026-09-18 明确纠正）。实现见 `engine.notify_owner()`：向 `config/wechat_groups.toml` 的群级 `owner_id` 私聊发送；GeWe 客户端**没有** at-list 能力，群内 @ 做不到。客户群里只出现安抚文案，不出现对负责人的 @。
   - 失败处理：`notify_owner()` **绝不抛异常**——负责人未配置 / 私聊失败只记日志，不得影响已发出的客户回复。开关 `settings.owner_notify_enabled`（默认 `True`，`OWNER_NOTIFY_ENABLED`）。
   - `ReplyDeliverable.owner_notify_text` 由 `process_demand_bundle()` / `process_visual_query_bundle()` **透传合并**，别在合并时丢掉。
10. **路由闸门顺序是硬约束（2026-09-18 负责人决策，只增不删）**：
   - 固定优先级：**显式转人工 → `intent_confidence < 0.50` 静默 → `non_standard` 安抚 → 两个澄清闸门 → 中置信度转人工 → normal**。
   - **两个澄清闸门必须排在"中置信度转人工"之前**。理由有实测数值：`这两款检测报告麻烦提供下`(intent 0.72 / completeness 0.25) 与 `查一下产品`(0.55 / 0.20) 都是"标准需求只缺实体"，排在后面就会被转人工截走，客户永远拿不到那句澄清。
   - 调整顺序时**不要顺手动阈值**；`silent` 永远最优先。
11. **"没查到" ≠ "不存在"（只增不删）**：
   - 标准需求但取不到答案时，一律走 `insufficient_data_reply()`：客户文案由模型生成（`compose_insufficient_data_reply()`），并**私聊**负责人；`channel_used="structured_no_evidence"`。
   - 触发面已覆盖：`no_evidence` / `error` / 计划被校验拒绝 / 知识库检索抛异常 / 规划器给不出计划 / `status=ok` 但无任何可陈述事实。
   - **兜底文案与 prompt 都严禁暗示"该记录不存在"** —— 只有"没查到"为真。有专门测试守这条。
   - 执行器 `status="clarify"` 是**双重语义**：规划器自己的澄清问句（可转发）与 `QueryPlanRejected` 的内部校验文案（**绝不外泄**，曾把 `file 和 validity 操作必须选择一个已注册的附件字段。` 直接发给客户）。分流靠 `PLAN_REJECTION_REASONS` + `owner_notice_reason_for_failure()`。
12. **计数类计划必须显式渲染 `count`**：`op=count` 的信封是 `data={"count":N,"records":[],"items":[]}`、`source=null`。engine 只渲染 `source`/`records`，**漏读 `count` 会让 `raw_answer` 退回假文案「查询成功。」**，模型就答"暂未记录该信息"。该假文案已删除。
13. **`plan_query` 必须有异常边界**：模型返回非 JSON / 校验失败时抛专用异常 `QueryPlanUnavailable`（重试 1 次后），由 engine 降级为"资料不足 + 转人工"。**绝不能让它冒到 ASGI** —— 曾把 `/api/v1/query` 打成 HTTP 500，在微信回调节点上意味着客户一条回复都收不到。
14. **FastGPT 检索会成串自重定向，且开 `follow_redirects` 更糟（只增不删）**：
   - 现象：`POST /api/core/dataset/searchTest` 返回 308，`Location` **与请求 URL 完全相同**。
   - 实测冷却：间隔 1s/3s 仍 308，**6s/10s 恢复**；串行 4 次为 `[401, 308, 308, 308]`。
   - **因此必须保持 `follow_redirects=False`**（跟随会循环到 `Exceeded maximum allowed redirects`），改用**有界重试 3 次 × 3.5 秒**（`_post_with_retry`）。
   - **成因是背靠背请求触发的限流，不是随机故障**：静置 12 秒后单独跑同一题必通过。生产问题间隔约 2 分钟，一般不触发；**跑回归时要加 `--pause-between`**。
   - **仍须在 FastGPT 容器侧排查**该自重定向的根因，客户端重试只是缓解。

- **非标准需求只安抚 + 私聊提醒负责人，绝不反问**（会议 00:04:37：澄清属于标准需求）。安抚文案**必须由模型生成**（`compose_soothe_reply()`，temperature 0.7），常量只是兜底；**不得**复用通用 composer（它明确禁止承诺"安排人员跟进"，而这条链路必须且真实地承诺）。
- **"没查到" ≠ "不存在"**：标准需求取不到答案时走 `insufficient_data_reply()` → 客户文案模型生成 + 私聊负责人，`channel_used="structured_no_evidence"`。兜底文案与 prompt 都严禁暗示"该记录不存在"。
- 执行器 `status="clarify"` 是**双重语义**：规划器自己的澄清问句（可转发）vs `QueryPlanRejected` 的内部校验文案（**绝不外泄**）。分流靠 `PLAN_REJECTION_REASONS` + `owner_notice_reason_for_failure()`。
- **人工介入即静默**：`claim_ready_tasks` 只领 `waiting_quiet`，`human_active` 结构性不可达。
- **命中规则提示、内部条件文案、Markdown 绝不能出现在客户气泡里**（会议明确点过这条）。
- **改路由顺序时不要顺手动阈值**；`silent` 永远最优先。

## 群策略热加载（2026-09-23 新增）

**背景**：加客户群是高频运维动作，而此前每加一个群都要重启服务——既慢，又要重新核对公网回调地址，纯数据改动不该承担这个风险。

**实现**：`core/wechat_groups.py` 新增 `WechatGroupsProvider`，以 `(st_mtime_ns, st_size)` 为戳监听文件变化；`AssistantEngine.groups_config` 改为**属性**，每次读取时按需重载，命中未变化则复用已解析对象（不产生额外 IO 压力）。

**行为约定**：

| 场景 | 行为 |
| --- | --- |
| 新增/修改 `[[groups]]` | 下一跳消息即生效，**无需重启** |
| TOML 语法错误或校验失败 | **保留上一份可用配置**并落 `logger.exception`，服务不中断、群回复不受影响 |
| 文件被删除 | fail closed（群处理整体停用），与 `WechatGroupsConfig.load` 原有语义一致 |
| 坏文件未修改 | 戳已记录，不会每条消息重复解析与重复刷日志 |

**注意**：属性赋值（`engine.groups_config = ...`）仍然可用，语义是**固定**该配置、跳过热加载——测试与自带策略集的调用方依赖这一点。热加载只对**未赋值**的引擎实例（即现网 `app.py` 构造的那一个）生效。

**仍需重启的情形**：改动 `src/` 下任何 Python 源码（含本模块自身）都必须重启，见上条运维纪律。

## 安抚话术可切固定文案（2026-09-23 新增）

**背景**：客户提出「未命中标准意图」的需求时，此前那句话由模型现写（措辞更像真人，但客户/负责人无法预知会收到什么）。负责人希望**可以选**改成固定一句「收到，我们加急处理」。

**实现**：`config/wechat_groups.toml` 的 `[global]` 新增两个参数，由 `WechatGroupsConfig` 解析、`AssistantEngine.compose_soothe_text()` 读取。

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `soothe_mode` | `"model"` | `model` = 模型现写；`fixed` = 用下面那句固定文案 |
| `soothe_fixed_reply` | `"收到，我们加急处理"` | `fixed` 模式实际发出的句子 |

**行为约定**：

| 场景 | 行为 |
| --- | --- |
| `soothe_mode = "model"`（默认） | 与改动前**完全一致**：模型现写；模型不可用时回退 `NON_STANDARD_SOOTHE_REPLY` |
| `soothe_mode = "fixed"` | 直接返回 `soothe_fixed_reply`，**不产生任何模型调用** |
| `fixed` 但文案被写成空串 | 退回模型生成，**不会发出空气泡** |
| 切换模式 | 改 TOML 即热加载，**下一跳消息生效，无需重启** |
| `soothe_mode` 写成非法值 | 校验失败 → **保留上一份可用配置**并落日志，服务不中断 |

**边界**：只影响「安抚」这一条路径，**不碰**资料不足文案（`INSUFFICIENT_DATA_FALLBACK_REPLY`）、澄清问句与人工兜底文案。

## 群聊天记录本地归档（2026-09-23 新增）

**背景**：负责人要求把**已配置群的聊天记录都存下来**，先落本地库，后续要做一个 **web 前端来复现这些聊天记录**。

**实现**：新增 `core/chat_log.py`（`ChatLogStore`，SQLite）。库文件 `data/chat-log.db`（`data/` 已 gitignore，**不会推上 GitHub**）。正文按负责人决策**明文存储**——便于直接查询、也便于日后整体迁移到正式库；代价是本机文件可读。

**为什么单开一个库，而不是复用现有两个**：`conversation-state.db` 是**只存元数据、刻意不存正文**的（幂等与重放安全的不变量），`payload-vault.db` 是**加密且短命**的（只为还原一条待处理需求）。归档表是只增不减、宽行、且不参与任何回复决策的读多写少表，混进前两者会把一张持续增长的表放到消息热路径上。

**写入时机**：

| 时机 | 内容 |
| --- | --- |
| 回调进来、**路由之前** | 群内**每一条**入站消息（客户 + 客服），含未 @机器人、被策略拦掉的 |
| 机器人**实际发出**回复之后 | 出站文本与附件（带 `channel_used` 与 `task_id`），**只记 `DispatchOutcome` 里真正发成功的部分**——文本发送失败、附件无公网 URL 或发送超时的，**不落行** |

**只写已配置的群**（`config/wechat_groups.toml` 里有的），私聊与未配置群**一条不写**。

**明确不记**：`mode = "shadow"` 群（回复根本没发出去）、机器人私聊负责人的提醒（属于另一个会话）。

**幂等**：入站按 `(direction, chat_id, message_id)` 唯一键去重，GeWe 重试回调不会长出重复气泡；出站无平台 ID，每次发送新增一条。

**出站准确性**：`dispatch_outbound` 逐条 try/except、**从不抛异常**，所以「调用返回」不代表「客户收到」。它返回 `DispatchOutcome(sent_text, sent_media_ids)`，归档只写实际发成功的部分——这条不变量审计后补强的，改动 `dispatch_outbound` 时**必须保持返回 outcome 且只记成功项**，否则档案里会出现「显示已发出、实际没发到」的假气泡。

**为空的前端字段要理解清楚**：`sender_name` 取 GeWe 回调里的昵称字段，**当前 GeWe 不返回，所以基本为空**——前端应回退显示 wxid，不要以为存漏了。被 @ 的昵称单独存在 `metadata.mentions`（解析器会把 `@昵称` 从正文里删掉，这里留一份以便复现）。引用信息在 `quoted_msg_id` / `quoted_type` / `quoted_text`，引用媒体的 XML 在 `metadata.quoted_media_xml`。

**容错**：归档是**尽力而为**，全程 try/except——库写不进去只会落日志，**绝不影响给客户回消息**；`__init__` 里建库失败也只是把归档降级为关闭，不会让服务起不来。

**开关**（`.env`，改动需重启）：`CHAT_LOG_ENABLED`（默认 `true`）、`CHAT_LOG_DB_PATH`（默认 `data/chat-log.db`）。`GET /health` 的 `chat_log` 字段可看状态。

### 12.2 顺带修掉的三个既有缺陷（都不是本轮引入）

1. **计数类答案丢失**：`op=count` 的信封只有 `{count, records: [], items: []}`，engine 从不读 `count` → `raw_answer` 退回假文案「查询成功。」→ 模型只能答"暂未记录"。实测受害：工厂认证份数、商标注册证份数。
2. **内部校验文案泄漏给客户**：`QueryPlanRejected` 默认 `status="clarify"`，其 message 被原样转发 → 客户收到 `file 和 validity 操作必须选择一个已注册的附件字段。`。修法：`PLAN_REJECTION_REASONS` + `owner_notice_reason_for_failure()` 分流，6 个 reason 全部参数化测试。
3. **规划器解析失败打成 HTTP 500**：`plan_query` 无异常边界，模型返回非 JSON 时 `json.JSONDecodeError` 一路冒到 ASGI。在微信回调节点上等于客户零回复。修法：重试 1 次 + 抛 `QueryPlanUnavailable` + engine 降级。

### 13.3 气泡格式加固：`*` 尺寸分隔符被误当强调标记（**既有缺陷**）
